# Хендоф для `v1tusha/life-support` — что накопилось в нашем форке

**Кому:** v1tusha, автор `life-support` (`proxy.js` + `panel.ps1`).
**От кого:** WormAlien, форк живёт как `routing/keepalive-proxy.js` в
[WormAlien/hub-cc](https://github.com/WormAlien/hub-cc) — публичный репо,
можно смотреть глазами.

**Зачем документ.** Прокся из Discord у нас на стенде работает без нареканий, а новые люди,
которые качают `life-support` с гитхаба, жалуются на вылеты. Разница объясняется просто: мы
чинили косяки по ходу и в апстрим их не отдавали. Ниже — всё, что разошлось, с симптомом,
причиной, кодом и способом проверить. Твою архитектуру не трогаю: имена и структура у нас
уже другие, поэтому патчи приложить нельзя — только точки вставки.

**Основание для сравнения:** `main` на 2026-08-21, `proxy.js` 788 строк против наших 1111.
Каждый пункт ниже проверен грепом по твоему файлу, а не по памяти. Где ты сделал лучше нас —
написано отдельным разделом, это не вежливость, а два реальных пункта, которые мы забираем.
Что дописано после первой версии — в конце, раздел «Что изменилось в этом документе».

**Два пункта, которые стоит прочитать даже если остальное неинтересно:** 1.1 (`/model` роняет
клиент — этого фикса у тебя нет вообще) и 2.1a (на не-agentrouter шлюзах мульти-запрос стоит живых
денег, по полной цене запроса за каждый дубль).

## Раздел 1. От этого новые юзеры вылетают

### 1.1 `/model` роняет клиент — нет `count_tokens` (главное)

**Симптом у юзера:** пишет `/model`, CLI падает с
`Unable to validate model: undefined is not an object (evaluating 'z.usage.input_tokens')`.
Дальше сессия непригодна, человек идёт писать «не работает».

**Причина:** Claude Code перед показом моделей шлёт `POST /v1/messages/count_tokens`.
agentrouter и большинство New-API-шлюзов этот endpoint не реализуют → `404` (иногда HTML от
WAF). CC читает `usage.input_tokens` **с тела ошибки** и умирает на валидации.

**Проверено:** `grep -c count_tokens proxy.js` → `0`. Обработчика нет, запрос уходит на шлюз
как есть. Это тот же фикс, что уходил как PR #1 в `sse-keepalive-proxy` — видимо, не
доехал до `life-support`.

**Фикс:** перехватывать путь **до** апстрима и отвечать локальной оценкой. У нас
`keepalive-proxy.js:320-350` (функции) и `:478-492` (перехват, первым делом в обработчике,
сразу после `stats.requests += 1`):

```js
const COUNT_TOKENS_PATH = '/v1/messages/count_tokens';
function isCountTokens(method, reqPath) {
  return method === 'POST' && reqPath.replace(/\?.*$/, '') === COUNT_TOKENS_PATH;
}
// ~4 символа на токен. Точность не важна: CC использует это как проверку «модель есть».
function estimateTokens(body) {
  try {
    const r = JSON.parse(body.toString('utf8') || '{}');
    const sys = typeof r.system === 'string' ? r.system
      : Array.isArray(r.system) ? r.system.map(b => (b && b.text) || '').join('') : '';
    let chars = sys.length;
    for (const m of r.messages || []) {
      if (typeof m.content === 'string') chars += m.content.length;
      else if (Array.isArray(m.content)) for (const b of m.content) {
        chars += ((b && b.text) || '').length;
        if (b && b.type === 'tool_use') chars += JSON.stringify(b.input || {}).length;
      }
    }
    return Math.max(1, Math.ceil(chars / 4));
  } catch (e) { return 1; }
}

// в обработчике запроса, ДО makeUpstream:
if (COUNT_TOKENS_FALLBACK && isCountTokens(req.method, reqPath)) {
  const chunks = [];
  req.on('data', c => chunks.push(c));
  req.on('end', () => {
    if (aborted) return;
    const tokens = estimateTokens(Buffer.concat(chunks));
    log(`${req.method} ${reqPath} -> 200 (local estimate ${tokens})`);
    res.writeHead(200, { 'content-type': 'application/json; charset=utf-8' });
    res.end(JSON.stringify({ input_tokens: tokens }));
  });
  req.on('error', () => { aborted = true; if (!res.writableEnded) res.destroy(); });
  return;
}
```

Флаг `COUNT_TOKENS_FALLBACK = process.env.COUNT_TOKENS_FALLBACK !== '0'` — чтобы можно было
выключить, если шлюз юзера endpoint всё-таки умеет.

**Как проверить:**

```bash
curl -s localhost:8787/v1/messages/count_tokens \
  -d '{"model":"claude-opus-4-8","messages":[{"role":"user","content":"привет"}]}'
# → {"input_tokens":N}, а не 404
```
И в живом CC `/model` должен открыться, а не уронить процесс.

### 1.2 `UPSTREAM_TIMEOUT_MS = 90000` рубит живые запросы

**Симптом:** «висело-висело и отвалилось» на длинных ответах, в логе обрыв ровно на 90с,
клиенту в итоге `502`.

**Наш замер** на agentrouter (n=153, 20.08.2026, конфиг 12с/3): медиана **20.4с**, 75-й
перцентиль **32.5с**, худший ответ — **135.3с**. В следующем окне (21.08, n=376) худший был
уже **159.6с**. То есть 90с режет не аномалию, а хвост нормального распределения, и каждый
обрыв ещё и жжёт попытку.

У нас дефолт `600000`. Предложение: поднять (мы бы сказали минимум 300с) либо явно написать
в README, что 90с рассчитаны на быстрый шлюз.

### 1.3 Пустой `200` после долгого thinking уходит клиенту как есть

**Симптом:** `API returned an empty or malformed response (HTTP 200)`.

Шлюз иногда отдаёт `200` с пустым телом (ловили после долгого thinking). Твой код форвардит
это клиенту. У нас не-stream `200` с `application/json|text/plain` **всегда** дренится, и
если после `trim()` тело пустое — уходим в ретрай (`пустой 200 (попытка N)` в логе), а не
отдаём клиенту пустышку.

### 1.4 Мульти-запрос выедает бюджет ретраев — при `maxAttempts: 2` всегда

Смотри свой `scheduleМульти-запрос` (`proxy.js:533-544`): он перевзводит себя, а ограничен только
общим `launched >= cfg.maxAttempts`. Счётчик один на мульти-запросы и ретраи. Следствие при твоём
дефолте `maxAttempts: 2`:

```
20с тишины → дубль #2 → launched = 2 = maxAttempts
дубль возвращает транзиентную 500 «无可用渠道» → attemptDone → ретраить НЕЧЕМ
                                              → клиент получает ошибку
```

То есть один медленный запрос обнуляет всю защиту от транзиентных ошибок — а она у тебя
хорошая, с китайскими паттернами.

**Фикс (сделали у себя 21.08):** отдельный счётчик дублей. `maxHedges` (дефолт `1`) +
`maxAttempts: 3`. Нагрузка та же (дублей не больше одного), а ретрай остаётся:

```js
let hedgesLaunched = 0;            // рядом с launched

const scheduleМульти-запрос = () => {
  if (cfg.hedgeMs <= 0 || cfg.maxHedges <= 0 || settled || aborted || hedgeTimer !== null) return;
  if (launched >= cfg.maxAttempts) return;
  if (hedgesLaunched >= cfg.maxHedges) return;      // ← весь фикс
  hedgeTimer = setTimeout(() => {
    hedgeTimer = null;
    if (settled || aborted) return;
    stats.hedges += 1;
    hedgesLaunched += 1;
    makeUpstream();
    scheduleМульти-запрос();
  }, cfg.hedgeMs);
};
```
Плюс `patchNum(c.maxHedges, 1, 5, true)` в `loadConfig`/`applyPatch` — ручка тогда крутится
из панели без рестарта, как остальные.

**Тест на сам кэп** (у тебя `G` и `H` заняты — добавляй как `I`). Шлюз молчит на все
попытки, клиент уходит через 4×`hedgeMs`, шлюз обязан увидеть ровно две копии:

```js
mode = 'hangall'; seen = 0;                    // новый режим: держим ВСЕ ответы молча
await askAbort(HEDGE_MS * 4);                  // клиент сам рвётся
assert.strictEqual(seen, 2, `при maxHedges=1 копий должно быть 2, а не ${seen}`);
```
Проверь, что тест не зелёный по случайности: с `MAX_HEDGES=5` он обязан падать с «увидел 3».

**Заодно цифра в защиту твоих 20с.** Мы неделю ходили на 12с и вернулись к 20с — вот почему.
Два окна одного дня на живом agentrouter, считано по логу:

| | 12с / 3 / кэпа нет | 20с / 3 / дублей ≤1 |
|---|---|---|
| ответов | 450 | 376 |
| дублей запущено | 174 (0.39 на запрос) | **95 (0.25)** |
| из них победили | 81 = **47%** | 64 = **67%** |
| запросов «сдались» | 3 | **1** |

На 20с дубль перестаёт быть мусорным: 75-й перцентиль ответа как раз ≈20с, поэтому дубль
летит ровно в худшую четверть запросов, где оригинал уже, скорее всего, не придёт. На 12с он
летел в середину распределения и в половине случаев проигрывал гонку своему же оригиналу.
Так что твой дефолт `hedgeMs: 20000` — правильный, менять надо только счётчик.

**Как НЕ надо это читать** (нас самих чуть не увело): медианы этих окон — 7635мс против
9880мс, и по ним кажется, что «после правки стало хуже». Но доля запросов, где шлюз молчал
дольше 10с, выросла с 36% до 46% при одинаковом `preCommitMs` — то есть просел сам шлюз.
Сравнивать медианы разных часов у agentrouter нельзя вообще; годятся только отношения внутри
одного окна (сколько дублей запущено против сколько победило).

### 1.5 `maxSockets: Infinity` — пачки обрывов TLS у юзеров с VPN

**Симптом:** `Client network socket disconnected before secure TLS connection was
established`, приходит кластерами, а не по одному. Особенно у тех, кто гоняет шлюз через
TUN-VPN (у нас Happ + sing-tun, но это про любой TUN).

**Причина:** оба реквестера идут через глобальный агент Node — `keepAlive: true`, но
`maxSockets: Infinity`. Мульти-запрос + ретраи = пачка одновременных TLS-рукопожатий, часть из них
TUN роняет.

```js
const MAX_SOCKETS = Number(process.env.MAX_SOCKETS || 16);
const httpsAgent = new https.Agent({ keepAlive: true, maxSockets: MAX_SOCKETS });
const httpAgent  = new http.Agent({ keepAlive: true, maxSockets: MAX_SOCKETS });
const agentFor = requester => (requester === https.request ? httpsAgent : httpAgent);
// ...и в опции запроса: agent: agentFor(upRequester),
```

Побочно это ускоряет: замер 20.08 — первое рукопожатие через туннель ~0.5с, дальше сокет
переиспользуется и запросы идут за ~0.25с. То есть налог разовый на всплеск, а не на каждый
запрос.

## Раздел 2. Не краши, но качество

### 2.1 Цена убитого дубля — замерено, забирай в свой тюнинг-док

Вопрос, который висел с самого появления мульти-запроса: платим ли мы за дубль, которого порвали.
Замер 21.08.2026 на свободном ключе agentrouter (расход был ровно $0, чтобы дельта была
чистой), рвали `req.destroy()` — ровно судьба проигравшего:

| сценарий | списано | байт получено | доля от полной цены |
|---|---|---|---|
| запрос до конца (33.5с) | **2.0066¢** | 8153 | 100% |
| порван до первого байта (1.5с) | 0.0306¢ | 0 | 1.5% |
| порван на 20-й секунде, уже стримил | **0.0066¢** | 920 | **0.3%** |

Порванный **позже** стоил меньше, чем порванный раньше → шлюз тарифицирует по факту
завершения генерации, а не по сгенерированному. Вывод для твоего комментария про
мульти-запросырование: «дублей побольше» — плохо только нагрузкой (полоса шлюза, пачки для WAF,
рукопожатия через туннель), деньгами это не пахнет. И отдельно: идея «не мульти-запросыть большие
контексты» бессмысленна — цена дубля не зависит от размера ввода.

### 2.1a Но на New-API-форках всё наоборот: дубль = полная цена запроса

Тот же замер на двух других шлюзах (те же CC-заголовки, тот же `req.destroy()` на 20-й
секунде) дал ровно обратное, и это важно, потому что твой README обещает совместимость с
New API:

| шлюз | полный ответ (2000 токенов) | крошечный (16 токенов) | **убитый дубль** |
|---|---|---|---|
| `agentrouter.org` | 2.0066¢ | — | 0.0066¢ (0.3%) |
| `tabitoken.com` | 50¢ | **50¢** | **50¢ (100%)** |
| `gorouter.app` | 20¢ | **20¢** | **20¢ (100%)** |

У них тариф **плоский за запрос**: цена не зависит ни от числа токенов, ни от того,
дочитали мы ответ или порвали. Значит на таком шлюзе каждый мульти-запрос-дубль — это полная цена
запроса, купленная за страховку, которая ускорения не даёт.

У нас из этого сделан per-host дефолт — три строки после объявления дефолтов:

```js
// Шлюзы с ПЛОСКИМ тарифом за запрос: убитый дубль списывается целиком.
const FLAT_RATE_HOSTS = new Set(['tabitoken.com', 'gorouter.app', 'xpeach.codes', 'api.justwoker.icu']);
if (FLAT_RATE_HOSTS.has(upstream.hostname)) DEFAULT_CFG.maxHedges = 0;
```

Пре-коммит и пинги при этом остаются — они не стоят ничего и именно они держат клиента.
Тебе достаточно знать порог: **если `UPSTREAM` не agentrouter, мульти-запрос по умолчанию лучше не
включать**, а в README написать, что `hedgeMs` осмысленен только на шлюзах с потокенным
тарифом.

Мелочь, но всплыла сразу: при `maxHedges = 0` логи не должны писать «мульти-запрос 20000ms» — иначе
человек читает лог и думает, что мульти-запрос работает. У нас теперь один хелпер на все сообщения:

```js
const hedgeOff = c => !(c.hedgeMs > 0 && c.maxHedges > 0);
```

**Дефолта тут оказалось мало — мы в итоге прибили это гвоздём.** Дефолт перебивается
`config.json`, env и панелью, то есть человек, у которого в файле с прошлых экспериментов
лежит `maxHedges: 3`, продолжит платить дважды за каждый висяк и не узнает об этом. Поэтому
на плоскотарифных хостах ручка зажимается **после** чтения конфига и на **каждый** патч:

```js
const ALLOW_PAID_HEDGE = process.env.ALLOW_PAID_HEDGE === '1';
const PAID_HEDGE_HOST = FLAT_RATE_HOSTS.has(upstream.hostname) && !ALLOW_PAID_HEDGE;

function clampPaidМульти-запрос(why) {
  if (!PAID_HEDGE_HOST || !(cfg.maxHedges > 0)) return false;
  log(`${why}: у ${upstream.hostname} тариф плоский за запрос — дубль стоит столько же, `
    + `сколько сам ответ. maxHedges ${cfg.maxHedges} → 0 (перебить: ALLOW_PAID_HEDGE=1)`);
  cfg.maxHedges = 0;
  return true;
}

loadConfig();
if (clampPaidМульти-запрос('старт')) saveConfig();   // и ещё раз в конце applyPatch()
```

Да, это сознательное неуважение к значению в файле — и здесь, по нашему мнению, так и надо:
«не сжечь чужой баланс» дороже, чем «выполнить любую цифру, которую вписали». Дверь для
осознанного случая одна и явная — `ALLOW_PAID_HEDGE=1` в env процесса.

Чтобы это не читалось как поломка панели, `/__state` отдаёт `flatRate` и `paidМульти-запросLocked`:
по ним панель глушит ручку с тултипом-причиной, пишет в статус «мульти-запрос выкл — тариф плоский,
дубль стоит как ответ» вместо безликого нуля, и если дубли всё же попытались поднять —
говорит прямо, что прокси оставил `0`. Молча вернувшийся ноль выглядит как «панель не
сохраняет настройку», и следующим шагом человек идёт искать баг в панели.

**Как замерять это самому** (нам понадобилось два запроса на шлюз): взять ключ со
`spent = 0`, читать расход через `GET https://<host>/dashboard/billing/usage?start_date=…
&end_date=…` с `Authorization: Bearer <ключ>` — эндпоинт есть у всех New-API-форков, отдаёт
`total_usage` в центах и авторизуется самим ключом, куки не нужны. Дальше два запроса: один
дочитать до конца, второй убить через `req.destroy()` на 20-й секунде — это ровно то, что
делает `settle()` с проигравшим. Грабля: путь `/v1/messages` при базе БЕЗ `/v1`, иначе
`404` на двойном `/v1`.

Побочно из того же замера — прямо в тему пункта 1.1: на плоском шлюзе каждый `/model`
без `count_tokens`-fallback стоил бы 20–50¢ живых денег, а не только ронял клиент. И
отдельный вывод для тех, кто ремапит haiku: на плоском тарифе короткий вызов сабагента
стоит столько же, сколько полный ответ opus — ремапить туда haiku бессмысленно.

`xpeach.codes` замерить не удалось — все ключи отдают `403 User has been banned`.
`api.justwoker.icu` (пятый инстанс, `:20158`, добавлен 22.08) тоже не замерен и попал в
список по аналогии. Там же — та самая грабля с базой: `POST /v1/messages` отдаёт 200,
`POST /v1/v1/messages` — 404, поэтому в `UPSTREAM` идёт корень `https://api.justwoker.icu`.
И отдельная причина не мульти-запросыть: шлюз подмешивает свой системный промпт, тривиальный
запрос уже стоит `input_tokens: 7166`.

### 2.2 `winBy` — кто принёс ответ

Без этой цифры `hedgeMs` подбирается наугад. Мы пишем на каждый ответ, чья попытка его
принесла, и держим агрегат в `/__state`:

```
POST /v1/messages winner: первый (попытка #1 из 1) за 8431ms
POST /v1/messages winner: мульти-запрос  (попытка #2 из 2) за 19304ms

curl -s localhost:8787/__state | grep -o '"winBy":{[^}]*}'
# {"первый":612,"мульти-запрос":38,"ретрай":4}
```

Как читать: `мульти-запрос` близко к нулю → дубли только грузят шлюз, `hedgeMs` поднимать; `ретрай`
много → шлюз отдаёт транзиентные ошибки, дело не в мульти-запросе. Наш свежий срез при 12с: из 174
дублей побеждали 81 (18%) — то есть **больше половины дублей были мусором**, и это был
прямой сигнал уйти на 20с.

### 2.3 CC-заголовки как fallback — для не-CC клиентов

У agentrouter перед API стоит Aliyun WAF, который пускает только запросы, похожие на Claude
Code: `user-agent: claude-cli/…` → 200, `curl/8.x` → `401 unauthorized client detected`
(проверено 16.08). Живой CC эти заголовки присылает сам, поэтому у твоих юзеров с CC всё
хорошо — но кто придёт с SDK, свой обвязкой или просто curl'ом, упрётся в 401 и решит, что
дело в проксе.

Мы доливаем **только отсутствующие**, клиентские значения не перебиваем:

```js
const CC_FALLBACK_HEADERS = {
  'user-agent': 'claude-cli/2.1.158 (external, sdk-cli)',
  'anthropic-version': '2023-06-01',
  'x-app': 'cli',
};
for (const [k, v] of Object.entries(CC_FALLBACK_HEADERS)) if (!headers[k]) headers[k] = v;
```

### 2.4 `wantsStream` стоит проверять метод и путь

У тебя `wantsStream(headers, body)` смотрит только на `accept` и `stream: true` в теле. У
нас `wantsStream(method, reqPath, headers, body)` дополнительно требует `POST` и путь ровно
`/v1/messages` (с отрезанным query). Иначе любой посторонний `POST` со `stream:true` получит
пре-коммит SSE — а после пре-коммита статус уже не изменить, все ошибки уходят in-band.

### 2.5 Эхо имени модели (опционально, возни много)

Если юзер пинит 1M-контекст, модель называется `claude-opus-5[1m]`. Шлюз в ответе
возвращает **своё** имя, CC считает окно по нему и суффикс теряется. Мы переписываем поле
`model` в ответе на то, что просил клиент (`MODEL_ECHO`, `patchSseChunk`/`flushSseEcho` для
SSE и `rewriteModelJson` для обычного тела). Пункт честно опциональный: реализация
неприятная, потому что SSE надо патчить по границам событий.

### 2.6 Дефолты — в одном месте, и прокси сам сообщает их панели

Это не про баг, а про грабли, на которые мы наступили дважды и потеряли на них больше
времени, чем на все фиксы выше. У тебя те же условия для этого: `config.json` рядом со
скриптом приоритетнее кода, плюс панель со своими подсказками.

**Что было у нас.** Обкатанные цифры лежали в четырёх местах: литералы в коде, плейсхолдеры
инпутов в UI, env в скрипте перезапуска и ещё раз env в спавне. «Поставить мульти-запрос 20с для
всех» мы делали правкой не того слоя — на существующей машине всё перебивал её
`config.json`, а свежей установке доставались литералы кода, и это были **другие** цифры.
Плюс ручной перезапуск молча возвращал вкладку к числам, замороженным в скрипте.

**Что сделали.** Ровно две вещи, обе дешёвые:

```js
// 1. Единственное место, где живут цифры
const DEFAULT_CFG = { hedgeMs: 20000, maxAttempts: 3, maxHedges: 1, preCommitMs: 10000 };
const cfg = { hedgeMs: Number(process.env.HEDGE_MS || DEFAULT_CFG.hedgeMs), /* … */ };

// 2. Отдаём их наружу вместе с текущим конфигом
function publicState() {
  return { cfg: { ...cfg }, defaults: { ...DEFAULT_CFG }, /* … */ };
}
```

Дальше панель **не хранит копию чисел**: плейсхолдеры и кнопка «Рекомендованные» (ставит
поставочные значения одним нажатием) заполняются из `defaults`. И строка статуса сравнивает
`cfg` с `defaults`, а при расхождении пишет `⚠ не дефолт (hedgeMs, …)`.

Кнопка тут не украшение, а следствие приоритета `config.json`: **юзер, который однажды
покрутил ручки, останется на своих цифрах навсегда**, и твоё обновление прокси ему ничего
не привезёт. Пока расхождение не видно в UI, он об этом даже не узнает — и придёт с
«у меня медленно» на настройках полугодовой давности. Заодно per-host дефолт из 2.1a
приезжает в панель сам, без второй таблицы значений на её стороне.

**Но кнопки мало — её надо нажать.** Через день после этого стало ясно, что «доедет, если
юзер сам захочет» решает не ту задачу: тот, у кого от старого конфига течёт баланс, как раз
и не знает, что надо нажимать. Поэтому добавили версию набора дефолтов:

```js
const CFG_VERSION = 2;   // поднимать при КАЖДОЙ смене DEFAULT_CFG

function loadConfig() {
  // …прочитали файл в c
  const was = Number(c.v) || 1;
  if (was !== CFG_VERSION) {                     // конфиг прошлой версии не читаем ВООБЩЕ
    fs.writeFileSync(`${CONFIG_FILE}.v${was}.bak`, raw);   // прежние настройки не теряем
    log(`config версии ${was} устарел (сейчас ${CFG_VERSION}) — беру дефолты кода`);
    saveConfig();                                // переписали новыми дефолтами
    return;
  }
  // …обычное чтение ручек
}
// saveConfig пишет { v: CFG_VERSION, ...cfg }
```

Смысл в том, что теперь у тебя есть **рычаг раскатки**: поменял дефолт, поднял версию —
и он доехал до всех, включая тех, кто крутил ручки полгода назад. Осознанную настройку
**свежей** версии это не трогает: конфиг с `v: 2` читается как обычно. Файлы `.v<N>.bak`
имеет смысл сразу дописать в `.gitignore`, иначе они всплывут в `git status` у каждого.

Контракт `defaults` и саму миграцию мы закрыли тестами (`defaults` есть и в нём все ручки;
устаревший конфиг не применяется, уезжает в `.bak`, файл переписан с версией). Второй тест
стоит того, чтобы его написать: подкладываешь нарочно вредный конфиг (`hedgeMs: 77000`) и
проверяешь, что в `cfg` он не доехал.

## Что мы забираем у тебя

Сравнение двустороннее, и два пункта у тебя сделаны, а у нас нет:

1. **`retry-after`.** Ты уважаешь заголовок и ждёшь ровно столько, сколько попросил шлюз
   (`retryAfterMs`, тест `H`). У нас на 429 своя пауза `RETRY_DELAY_MS * attempt` поверх
   инструкции шлюза — то есть мы либо спешим, либо тупим. Берём.
2. **Origin-guard на служебных путях.** `if (req.headers.origin) → 403` перед `/__state` и
   `/__config` (тест `G`): любая открытая вкладка может отправить `POST` на localhost и
   выставить `hedgeMs: 1000`, устроив шлюзу лавину. У нас этой защиты нет; эксплуатировать
   её мешает только то, что наш дашборд ходит в прокси серверным мостом, а не из браузера.
   Guard всё равно правильный — вкручиваем.

Ещё, чтобы не потерял при переносе нашего: у тебя **общее** определение сжатия
(`enc !== '' && enc !== 'identity'`), и оно лучше нашего regex-списка — мы на своём
`gzip|deflate|br` словили `ZstdDecompressionError` от свежего CC и потом всё равно пришли к
твоей логике.

## Как это переносить

Файлы разошлись структурно (у нас `settle()`/`forward()`/`handleControl()`, у тебя
`pipeSSE()`/`abortAll()`/`handlePanel()`), поэтому diff бесполезен — ориентируйся по
пунктам выше. Наш файл целиком:
`routing/keepalive-proxy.js` в `WormAlien/Autoreger_Clean`, рядом:

- `routing/KEEPALIVE-TUNING.md` — все ручки по-человечески, таймлайн запроса, замеры,
  диагностика «прокси vs шлюз vs туннель»;
- `routing/test-hedge.js` — стенд A–I против фейкового шлюза (наш `G` = кэп дублей,
  `H` = контракт `defaults`, `I` = миграция устаревшего конфига). Нумерация наша: у тебя
  `G` и `H` уже заняты Origin-guard'ом и `retry-after`, так что свои три пойдут с `I`;
- `ARCHITECTURE.md` → «Мульти-запрос / ретраи keepalive» — приоритет слоёв конфига.

**Порядок, если брать не всё:** 1.1 (краши прямо сейчас) → 1.4 (тихо ломает ретраи) →
1.2 (одна цифра) → 1.5 (одна вставка) → 1.3 → 2.1a (деньги, если у твоих юзеров не
agentrouter) → 2.6 (чтобы следующий фикс дефолтов реально доехал до людей) → остальное по
вкусу.

**Грабля напоследок, из своего опыта.** Дефолты живут в трёх слоях — `config.json` рядом со
скриптом, env и литералы в коде — и приоритет именно такой. Мы дважды правили «дефолт для
всех» не в том слое: у свежей установки `config.json` нет вовсе, поэтому реально едут именно
литералы в коде, а у существующего юзера всё перебивает его `config.json`. Если поднимешь
`UPSTREAM_TIMEOUT_MS` или `maxAttempts`, у тех, кто уже покрутил панель, ничего не
изменится — стоит сказать это в релизной заметке, иначе они напишут, что фикс не работает.
Как мы это в итоге закрыли — пункт 2.6 (`CFG_VERSION`).
