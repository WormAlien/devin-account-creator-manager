# keepalive-proxy — настройка ручек

Шпаргалка по четырём крутилкам `routing/keepalive-proxy.js`. Один и тот же скрипт крутится
пятью экземплярами, у каждого свой порт и свой конфиг:

| порт | шлюз | конфиг |
|---|---|---|
| `20133` | agentrouter.org | `keepalive-config-20133.json` |
| `20155` | tabitoken.com | `keepalive-config-20155.json` |
| `20156` | gorouter.app | `keepalive-config-20156.json` |
| `20157` | xpeach.codes | `keepalive-config-20157.json` |
| `20158` | api.justwoker.icu | `keepalive-config-20158.json` |

🪤 **У JustWoker в `UPSTREAM` идёт корень `https://api.justwoker.icu`, без `/v1`** — как у
tabi/gorouter/xpeach, и по той же причине: `/v1/messages` инстанс добавляет сам, а с базой
`…/v1` получается `/v1/v1/messages` → `404` на каждый запрос (замер 22.08). Хост обязан быть
с поддоменом: `justwoker.icu` не резолвится.

## Зачем это вообще

Бесплатные/перепроданные шлюзы тормозят и обрываются. Claude Code этого не прощает: если
в поток долго не приходит ни байта — он рвёт запрос сам (`Stream idle timeout - no chunks
received`). Ручки прикрывают разные способы сдохнуть: пре-коммит и пинги — клиента,
хедж и ретраи — молчащий или штормящий шлюз.

## Жизненный цикл запроса

```
0с      запрос ушёл на шлюз
10с     тишина → ПРЕ-КОММИТ: открыли SSE клиенту, клиент видит «пошло»
10с+    каждые 5с → ПИНГ (пустой SSE-комментарий), клиент не отваливается
20с     тишина → ХЕДЖ: параллельный дубль №2 (и всё — maxHedges=1)
        кто ответил первым — тот и победитель, проигравшего рвём
                              (в логе: `winner: первый|хедж|ретрай`)
        транзиентная ошибка → ретрай, бюджет попыток хеджем не выеден
```

«Тишина» = от шлюза не пришли даже заголовки. Как только они пришли, гонка закрыта
(`settle()` в `keepalive-proxy.js`), и дубль уже не полетит — даже если генерация после
этого течёт минуту.

## Ручки

| Ручка | Что делает по-человечески | Дефолт | Крутить если |
|---|---|---|---|
| **Pre-Commit** `preCommitMs` | Шлюз молчит N мс → прокси сам открывает поток клиенту, не дожидаясь. Клиент видит «пошло», а не «пусто» | `10000` | Ловишь `no chunks received` → **уменьшить** (5000) |
| **Ping** `IDLE_MS` | Пока шлюз думает, каждые N мс кидает в открытый поток пустой комментарий, чтобы клиент не решил, что всё умерло | `5000` | Клиент отваливается по таймауту → **уменьшить**. Почти никогда не надо |
| **Hedge** `hedgeMs` | Шлюз молчит N мс → пускает **параллельный дубль** того же запроса, берёт кто первый ответил, проигравшего рвёт | `20000` | Много висяков → **уменьшить**. Шлюз захлёбывается → **увеличить** |
| **Max Hedges** `maxHedges` | Сколько параллельных дублей максимум на один запрос. Считается отдельно от `maxAttempts`, поэтому ретраи на транзиентные ошибки остаются целы | `1`; у `tabitoken`/`gorouter`/`xpeach`/`justwoker` — **`0`** | Хочешь вообще без дублей → `0`. Поднимать выше 1 — только с замером `winBy` в руках. На плоскотарифных шлюзах включать только зная, что каждый дубль = полная цена запроса |
| **Attempts** `maxAttempts` | Сколько всего попыток на запрос (ретраи + хеджи вместе) | `3` | Шлюз штормит → 4–5, но это ×N нагрузки |

`0` = выключить ручку (кроме `maxAttempts`, там минимум 1). Значения зажимаются:
`hedgeMs` 1–120с, `preCommitMs` 2–120с, `maxHedges` 0–5, `maxAttempts` 1–10 — опечатка
`hedgeMs: 5` не устроит шлюзу лавину.

## Как менять

**Приоритет:** `keepalive-config-<PORT>.json` → env (`HEDGE_MS` / `MAX_ATTEMPTS` /
`MAX_HEDGES` / `PRE_COMMIT_MS`) → дефолты в коде (объект `DEFAULT_CFG`).

1. **Дашборд** — вкладка провайдера, блок с крутилками. Без рестарта. Рядом кнопка
   **«Рекомендованные»**: ставит поставочные значения, которые прокси сам сообщил в
   `/__state → defaults`. Нужна именно потому, что `json` приоритетнее кода — кто однажды
   покрутил ручки, останется на своих цифрах, и обновление прокси ему ничего не привезёт.
   Если текущий конфиг разошёлся с поставочным, в строке статуса видно
   `⚠ не дефолт (hedgeMs, …)`.
2. **Руками, без рестарта:**
   ```bash
   curl -X POST localhost:20133/__config -d '{"hedgeMs":20000,"maxHedges":1}'
   curl -s localhost:20133/__state          # cfg + defaults + счётчики
   curl -s localhost:20133/__keepalive/api/status
   ```
3. **Для всех машин** — только правкой `DEFAULT_CFG` в коде: json-конфиги в `.gitignore`
   (per-machine runtime), на свежей установке работают именно дефолты кода. Плейсхолдеры
   инпутов и кнопка «Рекомендованные» подтягиваются из `defaults` сами — второй копии
   цифр в дашборде нет и заводить её не надо.
   **И сразу подними `CFG_VERSION`** — иначе правка не доедет до тех, у кого json уже
   есть (он приоритетнее кода). При смене версии прокси архивирует прежний файл в
   `keepalive-config-<PORT>.json.v<N>.bak` и переписывает его дефолтами.

## 🔒 Что нельзя включить даже руками

`maxHedges` на шлюзах из `FLAT_RATE_HOSTS` зажимается в `0` **после** чтения конфига и
**на каждый** `POST /__config`. Ни json, ни панель, ни curl хедж там не включат — только
запуск процесса с `ALLOW_PAID_HEDGE=1`. Это не паранойя: дубль на таком шлюзе стоит как
полный ответ (50¢ у tabitoken, 20¢ у gorouter), а скорости не даёт, поэтому дешевле
проигнорировать цифру в файле, чем сжечь чужой баланс. Прокси пишет в лог, что зажал, а
дашборд глушит ручку и объясняет причину в строке статуса.

`keepalive-restart.ps1` и спавн из `transparent-proxy.js` эти ручки **не передают** — это
осознанно. Раньше передавали, и ручной рестарт молча возвращал вкладку к замороженным в
скрипте цифрам.

**`Ping` — исключение:** только env-переменная `IDLE_MS` при запуске, в дашборде её нет,
нужен рестарт процесса.

## 💰 Дубль деньгами не стоит — стоит нагрузкой (замер 21.08.2026)

**Это про agentrouter. На New-API-форках (tabitoken, gorouter, xpeach, justwoker) — наоборот,
см. следующий раздел.**

Главный вопрос по хеджу: платим ли мы за убитый дубль? Замер на свободном ключе
(`luminousfen`, расход был ровно $0), запросы шли напрямую в `agentrouter.org` с
CC-заголовками, разрыв — `req.destroy()`, то есть ровно судьба проигравшего:

| сценарий | списано | байт получено | доля от полной цены |
|---|---|---|---|
| запрос до конца (33.5с) | **2.0066¢** | 8153 | 100% |
| порван до первого байта (1.5с) | 0.0306¢ | 0 | 1.5% |
| порван на 20-й секунде, уже стримил | **0.0066¢** | 920 | **0.3%** |

Порванный позже стоил **меньше**, чем порванный раньше — значит шлюз тарифицирует по
факту завершения генерации, а не по сгенерированному. Практический вывод: цену дубля
измеряем не в деньгах, а в

- **полосе шлюза** — он считает дубль отдельным запросом и делит на него ту же полосу;
- **пачках для WAF** — Aliyun WAF у agentrouter чувствителен к всплескам, ответ `403`;
- **TLS-рукопожатиях через туннель** — sing-tun часть одновременных роняет.

Поэтому порог «не хеджить большие тела» **не нужен**: цена дубля не зависит от размера
контекста, раз токены за убитого не списываются.

## 🚨 Плоский тариф за запрос: New-API-форки — там хедж стоит полную цену

Тот же замер на New-API-форках дал ровно обратное. Одна и та же цена за что угодно:

| шлюз | полный ответ (2000 токенов) | крошечный (16 токенов) | **убитый дубль** |
|---|---|---|---|
| `tabitoken.com` | 50¢ | **50¢** | **50¢ (100%)** |
| `gorouter.app` | 20¢ | **20¢** | **20¢ (100%)** |
| `agentrouter.org` | 2.0066¢ | — | 0.0066¢ (0.3%) |

Цена не зависит ни от токенов, ни от того, дочитали мы ответ или порвали его на 20-й
секунде. Отсюда три следствия:

1. **Хедж на этих шлюзах выключен из коробки** (`maxHedges: 0` для хостов из
   `FLAT_RATE_HOSTS` в `keepalive-proxy.js`). При 0.25 дубля на запрос это было бы +25%
   к счёту за страховку, которая скорости не даёт. Пре-коммит и пинги остаются — они
   бесплатны и именно они держат клиента.
2. **`count_tokens`-fallback экономит реальные деньги, а не только чинит `/model`.**
   Без него каждый `/model` уходил бы на шлюз и стоил 20–50¢.
3. **Гнать haiku-тир сабагентов на плоский шлюз бессмысленно** — короткий вызов стоит
   столько же, сколько полный ответ opus.

`xpeach.codes` в списке по аналогии (тот же форк), но **не замерен**: все три ключа
отдают `403 User has been banned`. Заработает — прогнать замер и решить по цифрам.
`api.justwoker.icu` — тоже по аналогии и тоже не замерен. Дополнительный довод против
хеджа там: шлюз подмешивает свой системный промпт, и тривиальный запрос уже стоит
`input_tokens: 7166` (замер 22.08) — то есть дубль дорог даже при токенном тарифе.

**Как замерять в следующий раз:** ключ со `spent = 0` из `routing/<prov>-sessions.json`,
расход читать через `GET https://<host>/dashboard/billing/usage?start_date=…&end_date=…`
с `Authorization: Bearer <ключ>` (отдаёт `total_usage` в центах, куки не нужны). Дубль
эмулировать `req.destroy()` через 20с после старта — это ровно то, что делает `settle()`
с проигравшим. Путь запроса — `/v1/messages` без `/v1` в базе (иначе `404` на двойном
`/v1`, грабля документирована).

## ⚠️ Агрессивный хедж делает хуже, не лучше

Замер на живом agentrouter (v1tusha, 15.08.2026):

| настройка | результат |
|---|---|
| `hedgeMs=5000` + 5 попыток | ~×3 нагрузки, ответы поехали **8с → 15–30с** |
| `hedgeMs=20000` + 2 попытки | вернулось к **6.6–8.6с** |
| **`hedgeMs=20000` + 3 попытки, дублей ≤1** | текущий дефолт из коробки |

Дубль не бесплатный: шлюз считает его отдельным запросом и делит на него ту же полосу.
Без причины не трогать.

## Диагностика: кто виноват

```bash
# 1. Прокси вообще жив и что отдаёт?
curl -s localhost:20133/__state
grep -aE "$(date +%Y-%m-%d)" keepalive-proxy.log | grep -aoE '\-> [0-9]+' | sort | uniq -c

# 2. Ошибки апстрима (не наши!)
grep -a 'upstream error\|upstream stream error\|все попытки исчерпаны' keepalive-proxy.log | tail -20

# 3. Хвост латентности шлюза
grep -aE "$(date +%Y-%m-%d)" keepalive-proxy.log | grep -aoE '[0-9]+ms$' | tr -d 'ms' | sort -n | tail -10
```

Как читать:

| симптом | кто виноват |
|---|---|
| `-> 200` много, `upstream error` в логе | **шлюз или туннель**, прокси прикрывает |
| `Connection closed mid-response` у клиента | апстрим оборвался **после** пре-коммита — дописывать нечего |
| `Stream idle timeout - no chunks received` | апстрим сдох **до** пре-коммита + `все попытки исчерпаны` |
| `Client network socket disconnected before secure TLS` | не дошло до рукопожатия → см. «Туннель» ниже |
| латентности 50–100с при `-> 200` | шлюз реально медленно генерит, ручки не помогут |

## Туннель — рычаг больше всех ручек (2026-08-20)

Трафик к шлюзам идёт через VPN **Happ** (`happ-tun`, sing-tun + xray, системный прокси
`127.0.0.1:10809`). Проверяется так:

```bash
curl -s -o /dev/null -w "connect=%{time_connect}s tls=%{time_appconnect}s\n" \
  -I https://agentrouter.org/api/hello
```

`connect≈0.001s` при `tls≈0.5s` — признак TUN-режима: TCP терминируется локально, реальный
коннект происходит уже на фазе TLS. Отсюда два следствия:

- **Висяки `tls=0.000000, total=20s`** (примерно 1 из 5 одиночных запросов) — это туннель не
  смог поднять исходящее плечо. Ни прокси, ни шлюз тут не виноваты, ручки не спасут.
- **~0.5с на рукопожатие** платится на **первое** соединение; дальше Node переиспользует
  сокет и запросы идут за ~0.25с (замерено 2026-08-20 на серии из 8 запросов). То есть налог
  разовый на всплеск, а не на каждый запрос. `agentrouter.org` — это Aliyun ALB в
  **ap-southeast-1 (Сингапур)**, IPv4-only, две ноды (`8.214.161.192`, `8.214.160.125`),
  обе здоровы и равны. Официальное зеркало `ps.air-outer.com` — тот же CNAME на те же
  IP, отдельного сервера за ним нет: помогает только если основной домен заблокируют,
  скорости не даёт. Выходная нода VPN ближе к SG/HK = меньше RTT.

## Кто победил — оригинал или дубль (главная цифра для настройки хеджа)

Прокси пишет на каждый ответ, чья попытка его принесла:

```
POST /v1/messages winner: первый (попытка #1 из 1) за 8431ms
POST /v1/messages winner: хедж  (попытка #2 из 2) за 19304ms
```

Агрегат — без грепа, сразу числом:

```bash
curl -s localhost:20133/__state | grep -o '"winBy":{[^}]*}'
# {"первый":612,"хедж":38,"ретрай":4}
```

Как читать:

| `winBy` | вывод |
|---|---|
| `хедж` близко к нулю | дубли не спасают, только грузят шлюз → `hedgeMs` **поднять** |
| `хедж` заметная доля | дубли реально вытаскивают висяки → оставить или чуть опустить |
| `ретрай` много | шлюз отдаёт транзиентные ошибки — смотреть `byStatus`, дело не в хедже |

Счётчики живут с момента старта процесса, после рестарта обнуляются.

### Замеры на живом agentrouter (2026-08-20, :20133)

Первый замер с появлением `winBy`. Конфиг **12с / 3 попытки**, n=153 ответа за ~64 мин:

| | |
|---|---|
| медиана ответа | **20376 мс** |
| 25% / 75% | 7488 мс / 32456 мс |
| худший | 135298 мс |
| принёс оригинал | 86 (56%), медиана **8817 мс** |
| принёс дубль | 67 (44%), медиана **31629 мс** |
| ошибок / ретраев | 3 / 0 |

Как читать: шлюз почти не отдаёт ошибок — он **замолкает**, все дубли ушли в ответ на
тишину. Дубли отрабатывают (44% ответов), но их запущено больше, чем самих запросов
(161 на 163), то есть шлюзу уходит двойной трафик — и в 56% случаев дубль был лишним.
Когда оригинал побеждает, он укладывается в 8.8с — ровно «хороший» диапазон из замера
выше. Общая медиана в 2.5 раза хуже. Отсюда гипотеза: часть зависаний мы создаём сами.

Проверка гипотезы — А/Б на медиане, а не на догадках. Зафиксировать границу в логе,
переключить конфиг без рестарта, через час сравнить:

```bash
N=$(grep -ac 'winner:' keepalive-proxy.log)          # граница ДО переключения
curl -s -X POST localhost:20133/__config -d '{"hedgeMs":20000,"maxAttempts":2}'
# ...час работы...
grep -a 'winner:' keepalive-proxy.log | tail -n +$((N+1)) \
  | grep -aoE 'за [0-9]+ms' | grep -oE '[0-9]+' | sort -n \
  | awk '{a[NR]=$1} END{printf "медиана %dмс из %d\n", a[int(NR/2)], NR}'
```

`winBy` для А/Б не годится — он не обнуляется на `POST /__config`, только на рестарт.
Поэтому сравнивать по логу с отсечкой.

**Результат 20с/2** (n=83, тот же вечер, сразу после базы):

| | 12с / 3 | 20с / 2 |
|---|---|---|
| медиана | 20376 мс | **19264 мс** |
| 25% (быстрые) | 7488 мс | **6459 мс** |
| 75% (медленные) | **32456 мс** | 36613 мс |
| худший | 135298 мс | 127779 мс |
| принёс дубль | 44% | 37% |
| дублей на запрос | ≈0.99 | **≈0.50** |

Медиана одинаковая — разница 5% при таком разбросе это шум. Видно честный обмен: реже
дубли → быстрые запросы быстрее (меньше лишней нагрузки), медленные медленнее (некому
вытаскивать). Решает нагрузка: **при той же скорости вдвое меньше дублей**, а WAF шлюза
чувствителен к пачкам — значит меньше риск словить `403`.

**Вывод: держим `hedgeMs: 20000`.** Возврат к 12с смысла не имеет: он не быстрее, только
шумнее. А вот `maxAttempts: 2` из этого замера в дефолты **не пошёл** — вместо него
21.08 появилась отдельная ручка `maxHedges: 1` при `maxAttempts: 3`. Разница
принципиальная: `maxAttempts=2` резал заодно и ретраи, поэтому на транзиентную `500`
(`无可用渠道`) повторять было нечем, если попытку уже съел хедж. Отдельный счётчик
дублей даёт тот же ×0.5 по нагрузке и сохраняет ретрай. Дальше медиану двигает не хедж,
а сам шлюз (он молчит десятки секунд и почти не отдаёт ошибок) — см. «Туннель» и общий
вывод: ускорять надо сменой шлюза, а не ручками.

### Два окна одного дня: 12с/3 против 20с/≤1 (2026-08-21, :20133)

Считано по логу, границы — строки старта процесса. Это лучшее обоснование текущих
дефолтов, и заодно пример того, как НЕ надо читать такие замеры:

| | 12с / 3 / кэпа нет | 20с / 3 / дублей ≤1 |
|---|---|---|
| ответов | 450 | 376 |
| медиана | 7635 мс | 9880 мс |
| 25% / 75% | 5475 / 15104 мс | 6587 / 20036 мс |
| дублей запущено | 174 (0.39 на запрос) | **95 (0.25)** |
| принёс дубль | 81 | 64 |
| **дублей впустую** | **53%** | **33%** |
| запросов «сдались» | 3 | **1** |
| шлюз молчал >10с | 36% запросов | 46% запросов |

**Медиану сравнивать нельзя** — доля запросов с тишиной дольше 10с выросла с 36% до 46%,
а `preCommitMs` в обоих окнах одинаковый, то есть это чистый признак: шлюз во втором окне
просел сам. Разница 7.6с → 9.9с про agentrouter, а не про хедж.

**Что действительно видно:** на 20с дубль стал осмысленным. Из 95 запущенных победили 64
— **67%**, против 47% (81 из 174) на 12с. Причина простая: 75-й перцентиль ответа ≈20с,
поэтому дубль на 20с летит ровно в худшую четверть запросов, где оригинал уже, скорее
всего, не придёт. На 12с он летел в середину распределения и в половине случаев проигрывал
гонку оригиналу.

Отсюда и вывод про «выключить хедж совсем»: `maxHedges: 0` стоил бы те самые 64 ответа
(17% всех) — их принёс дубль. Хедж здесь не ускоритель, а страховка, и на 20с она
срабатывает по делу.
